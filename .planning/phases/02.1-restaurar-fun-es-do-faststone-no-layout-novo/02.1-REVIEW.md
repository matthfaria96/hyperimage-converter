## Summary

This is a re-review of the fix commits `3a99522..3d44194` (`git diff 94a722d..HEAD -- Sources Tests`), checked against the iteration-1 findings. Every test passes with the Xcode toolchain: 140 core tests and 20 app tests. The CLT toolchain cannot build the XCTest-based core tests.

**Iteration-1 findings verified as resolved:**

- **CR-01 is resolved.** `blockingChains` now flags any entry whose destination is the source of an entry that will not move, and repeats until nothing changes. Both `plan` and `undoPlan` use it.
  - Temporary names are visible and keep the extension (`hyperimage-tmp-<UUID>.<ext>`).
  - A rollback that fails goes through `rescue`, which never overwrites: it checks `fileExists` first, and `moveItem` refuses to overwrite anyway. The rescued file is recorded in `moved`.
  - I traced these cases and none of them loses a file or leaves an untracked one:
    - a phase-1 failure in the middle of a cycle `c→a, a→b, b→c` where `b` is locked: `a` is rescued as `a (HyperImage 1)`, and undo restores it
    - an undo partly blocked by a recreated name
    - a forward-chain rescue followed by undo
  - In the rare case where `rescue` itself fails, the file stays under a visible temporary name that keeps its extension (see IN-07).
- **WR-01 is resolved.** Dates are read only when `usesDate` is true. `records(for:)` runs in a `Task.detached`. It compiles under Swift 6 strict concurrency: `BatchConverter` and `InputItem` are `Sendable`, and `items` and `converter` are immutable captures, so there is no data race. After the await, a `run == generation` check stops a superseded run from writing state. Cancel latency during planning is noted in IN-05.
- **WR-02 is resolved.** `guard !Task.isCancelled` now runs before `info = loaded`.
- **WR-03 is resolved.**
  - `remainingHistory` keeps the moves that were not undone and re-points the rescued ones.
  - `applyRename` keeps the previous undo when nothing moved.
  - Conflicts and I/O failures are reported separately.
- **WR-04 is resolved.** The replaced extension goes through `withoutSeparators`. `isValidFileName` flags empty names, `.`, `..`, names containing `/`, and names over 255 bytes.
- **WR-05 is resolved.** `SearchReplaceRule.normalized()` pads or trims the pairs to 3 in `PersistedState.decode`.
- **WR-06 is resolved for its original scenario.** "Substituir" can no longer overwrite unrelated files when template output names are written in place. The fix goes too far, though: it also disables the "Pular" and "Perguntar" policies (new WR-01 below).
- **WR-07 is resolved.** `BatchRename.counts` now feeds the preview, and the chain test asserts `(0, 3)`.

**SAFE-01 still holds.** Input paths are still in `used`, and the skip-existing check only adds names to avoid. It never removes a reservation.

## Warnings

### WR-01: In-place template output now ignores the "Pular" and "Perguntar" overwrite policies, so every re-run creates `-2`, `-3`… duplicates

**File:** `Sources/HyperImageCore/Batch/ConvertSettings.swift:101-107` (interacts with `Sources/HyperImageCore/Batch/BatchConverter.swift:79-94`, `Sources/HyperImage/Convert/SettingsPanel.swift:300-305`)

**Issue:** `avoidDisk = templated && inPlace` applies whichever overwrite policy is chosen. `OutputPlanner` therefore never returns a destination that already exists. As a result, `BatchConverter.run` never sees an existing output in this mode:
- `skipExisting` (`.noToAll`) never skips anything.
- `askBeforeOverwrite` never prompts.

Example: the user converts `a.png` and `b.png` in place with template `Image#####` and the "Pular existentes" policy. The first run writes `Image00001.jpg` and `Image00002.jpg`. Re-running, for example after adding a third file, writes `Image00001-2.jpg`, `Image00002-2.jpg` and `Image00003.jpg`. The user asked for the existing outputs to be skipped, and gets duplicates of every file on every run. Under "Perguntar" no question is ever asked.

Only "Substituir" was a data-loss risk, and that is the only policy that needs the disk check. The fix report mentions this side effect, but it breaks a user-visible setting for two of the three policies.

**Fix:** Limit the disk avoidance to the policy that can overwrite without asking:
```swift
let overwritesSilently = !settings.askBeforeOverwrite && !settings.skipExisting
let avoidDisk = templated && inPlace && overwritesSilently
```
Then add an `OutputPlanner` test with `skipExisting = true` and an `exists:` stub returning true. It should assert that the planned name is the plain `Image00001.jpg`, which `run` will then skip.

## Info

### IN-01: `String(format: "%0Nd", Int)` truncates to 32 bits

**File:** `Sources/HyperImageCore/Naming/RenameTemplate.swift:41`

**Issue:** Unchanged from iteration 1. `%d` reads an `Int32`, and a persisted `startNumber` is not clamped.

**Fix:** Use `%0\(run)ld`, or clamp `startNumber` on decode.

### IN-02: Templates can produce hidden or whitespace-only names

**File:** `Sources/HyperImageCore/Naming/RenameTemplate.swift:59-62, 70-72`

**Issue:** Unchanged. `sanitized` does not trim spaces or strip a leading `.`, and `isValidFileName` accepts both. A template like `.x##` creates hidden files.

**Fix:** Trim spaces and strip leading dots in `sanitized`, or reject a leading `.` in `isValidFileName`.

### IN-03: Saving `mode = .rename` resets every setting if the user downgrades

**File:** `Sources/HyperImageCore/Batch/OutputRecipe.swift:4`, `Sources/HyperImage/App/PersistedState.swift:33-36`

**Issue:** Unchanged. An older build cannot decode the unknown `ConvertMode` value, so the whole decode falls back to `PersistedState()`.

**Fix:** Optional. Decode unknown raw values to `.convert`.

### IN-04: The "Converter" menu item opens the rename preview in Renomear mode

**File:** `Sources/HyperImage/App/HyperImageApp.swift:94`, `Sources/HyperImage/App/MainView.swift:93`

**Issue:** Unchanged. The menu label does not follow `mode.actionTitle`.

**Fix:** Use `mode.actionTitle` for the label.

### IN-05: Cancelling while outputs are being planned has no effect until planning ends, and the status reads "Processando 0 de 0"

**File:** `Sources/HyperImage/Convert/ConversionRunner.swift:61-69`, `Sources/HyperImage/Convert/SummaryBox.swift:139`

**Issue:** `Task.detached` is not a child of `task`, so `cancel()` does not reach it. `records(for:)` also has no cancellation checks. On a large or slow list, which is the case WR-01 was about, Cancel does nothing visible until every file has been stat'ed, `exists`-checked and possibly date-read. The run then ends as cancelled. While planning, `records` is empty, so `statusText` shows "Processando 0 de 0…". No data is at risk.

**Fix:**
- Wrap the call as `RenamePreviewSheet` does: `withTaskCancellationHandler { await work.value } onCancel: { work.cancel() }`.
- Check cancellation every N items inside `OutputPlanner`/`records(for:)`, or make it `throws`.
- Show "Preparando…" while `isRunning && records.isEmpty`.

### IN-06: `undoPlan` can flag an entry as a conflict because a *missing* file "holds" its name

**File:** `Sources/HyperImageCore/Naming/BatchRename.swift:87, 164-173`

**Issue:** `blockingChains` seeds `blocked` with the source keys of every conflict, including entries flagged only because `missing` is true (the file at `move.to` was deleted). That path is actually free, but any undo entry whose destination is that path is still flagged.

Example: forward `a→b`, `b→c`. The user deletes `b` (the original `a`). Undo then flags `c→b` too, even though `b` is free. Nothing is lost. `remainingHistory` drops the missing move, so a second Undo succeeds, but the first attempt reports a false conflict.

**Fix:** Seed `blocked` only with conflicts whose source still exists:
```swift
var blocked = Set(result.filter { ($0.conflict && FileManager.default.fileExists(atPath: $0.source.path)) || $0.unchanged }.map { key($0.source) })
```
Alternatively, pass the missing set in from `undoPlan`.

### IN-07: The rescue name can exceed 255 bytes, so `rescue` fails and the file stays under the temporary name

**File:** `Sources/HyperImageCore/Naming/BatchRename.swift:150-160`

**Issue:** `"\(base) (HyperImage \(n)).\(ext)"` adds about 18 bytes to the original name. If the original is close to 255 bytes, every candidate fails with ENAMETOOLONG. The loop tries all 999 candidates, and the file stays at `hyperimage-tmp-<UUID>.<ext>`. That name is visible and keeps the extension, and the failure message reports where the file is. It is still not in `moved`, so undo and the input list lose track of it.

**Fix:** Truncate `base` so that the candidate's `utf8.count` stays at or under 255. Stop the loop on errors other than "file exists".
