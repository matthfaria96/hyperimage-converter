# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-23T12:00:00Z
**Depth:** standard
**Files Reviewed:** 28
**Status:** issues_found

## Summary

Reviewed the changes since `dc3b0e7`: the new Batch Rename tab (plan / two-phase execute / undo), the output-name template in Batch Convert, the persisted-state additions and the new UI cards.

**Checks that passed:**

- **SAFE-01 holds for template output names.** `OutputPlanner` still reserves every input path, so a converted file never lands on a queued input. Swift `String` comparison and hashing treat NFC and NFD forms as equal, so an NFC template cannot slip past an NFD input name. I confirmed this on APFS.
- **Case-only renames work.** Renaming `a.JPG` to `a.jpg` goes through the temporary name, and undo handles it because of the lowercased `targets` check.
- **Same names in different folders are handled.** Names are compared by full path.
- **New persisted keys decode with their defaults.** `TolerantJSON` fills in the missing keys.
- **`FileManager.moveItem` never overwrites.** Swaps and plain renames are safe.

**Blocker.** I reproduced a realistic file-loss case. In the second phase, `BatchRename.execute` can fail to move a file to its new name. When that happens, it tries to move the file back to its old name. If an earlier entry in the same batch has already taken that old name, the move back fails too. The original file is then left as a hidden `.hyperimage-<UUID>` file with no extension. `plan` and `undoPlan` don't mark entries that depend on a skipped entry, so a plain, everyday batch triggers this.

The warnings cover:
- main-thread EXIF reads when output renaming is on
- an async task in `PreviewCard` that can show the wrong file's details
- undo throwing away its history after a partial failure
- the extension text from search and replace never being cleaned
- a possible crash from persisted state
- the "Substituir" policy now hitting unrelated files much more often

## Critical Issues

### CR-01: Batch rename / undo can strand an original as a hidden, extension-less `.hyperimage-UUID` file

**File:** `Sources/HyperImageCore/Naming/BatchRename.swift:57-67, 88-100, 106-115` (also `Sources/HyperImage/Rename/RenameActions.swift:9, 23`)

**Issue:** The conflict check in `plan` only looks at whether the destination file exists when that destination is *not* one of the source files (`existsOutside = !sources.contains(key) && …`). It assumes every source will be moved out of the way. That assumption is wrong when the source belongs to an entry that will itself be skipped (a conflict). That entry stays where it is, so any entry renaming onto it fails in phase 2. The rollback then tries to move the file back to its original name, which an earlier entry may already have taken. The file stays at its temporary name.

I reproduced this with the real `BatchRename.swift` and `RenameTemplate.swift`:
- Folder contents: `photo.jpg`, `IMG_0001.jpg` and `IMG_0002.jpg` (all in the list, in that order), plus `IMG_0003.jpg` (not in the list).
- Template: `IMG_####`.

```
photo.jpg    -> IMG_0001.jpg
IMG_0001.jpg -> IMG_0002.jpg
IMG_0002.jpg -> IMG_0003.jpg CONFLICT
renamed 1 failures ["…couldn't be moved… — o arquivo ficou em …/.hyperimage-E3C6…"]
.hyperimage-E3C64BA6-…  = ONE     <- original IMG_0001.jpg, now hidden with no extension
IMG_0001.jpg            = PHOTO
IMG_0002.jpg            = TWO
```

What the user sees:
- The preview lists `IMG_0001 -> IMG_0002` as an ordinary rename, not a conflict.
- The original is hidden in Finder, has no extension, and is not recorded in `moved`, so undo cannot bring it back.
- `AppModel.replace` maps `photo -> IMG_0001` while the old `IMG_0001` item stays in the list. The list now has two `InputItem`s with the same `id`, which SwiftUI `ForEach`/`Table` do not allow, and a later conversion would process the same file twice.

`undoPlan` has the same flaw. The `targets.contains(key(move.from))` check treats a name as free whenever some renamed file currently holds it, even if that file's own undo entry is skipped. Example: forward moves `IMG_0002->IMG_0001`, `IMG_0003->IMG_0002`, `photo->IMG_0003`. The user then creates a new `photo.jpg` and clicks Undo. The original `IMG_0003` ends up stranded the same way.

Other phase-2 failures feed the same path:
- a name longer than 255 bytes (not validated)
- a `/` in the extension (see WR-04)
- a file created between the preview and the confirm click

**Fix:**
1. In `plan` and `undoPlan`, repeat the check until nothing changes: an entry whose destination key is the source key of an entry that will not move (conflict or unchanged) must itself be marked as a conflict.
```swift
var blocked = Set(entries.filter { $0.conflict || $0.unchanged }.map { key($0.source) })
var changed = true
while changed {
    changed = false
    for i in entries.indices where !entries[i].conflict && !entries[i].unchanged
        && blocked.contains(key(entries[i].destination)) {
        entries[i].conflict = true
        blocked.insert(key(entries[i].source))
        changed = true
    }
}
```
2. In `execute`, make the rollback impossible to lose. If moving back to `entry.source` fails, move the temporary file to a visible, unique name that keeps the extension, for example `"\(base) (HyperImage \(n)).\(ext)"`. Report that URL, and add it to `moved` so undo and the input list stay consistent.
3. Temporary names should keep the original extension and should not start with a dot, so a crash between the phases leaves files a user can see.
4. Add tests for the chain-onto-a-conflict case and for a real swap (`a<->b`). The current `swapsNamesWithoutLosingFiles` test only renames `a->c`.

## Warnings

### WR-01: Output renaming reads the EXIF date of every file on the main thread, even when the template has no date token

**File:** `Sources/HyperImageCore/Batch/ConvertSettings.swift:89-91` (called from `Sources/HyperImage/Convert/ConversionRunner.swift:53`, which is MainActor because of `defaultIsolation`)

**Issue:**
- `OutputPlanner.destinations` calls `dates(item.url)`, which is `BatchConverter.fileDate`, for every item whenever `settings.rename` is on.
- `fileDate` opens a `CGImageSource` and reads the image properties.
- `ConversionRunner.start` calls `converter.records(for:)` synchronously on the main actor.

With thousands of files, or files on a network or external volume, clicking "Converter" freezes the UI. The default template `Image#####` doesn't even use the date. `BatchRename.plan` has the same eager date read; it runs detached there, but it still costs one disk read per file.

**Fix:** Only read the date when the template needs it, and build the records off the main actor.
```swift
let needsDate = settings.renameTemplate.range(of: #"\$[YMDHNS]"#, options: [.regularExpression, .caseInsensitive]) != nil
… date: needsDate ? dates(item.url) : .distantPast
```
Also move `converter.records(for:)` into the task, or into a `Task.detached`, inside `ConversionRunner.start`.

### WR-02: `PreviewCard` can show a different file's metadata (no cancellation guard)

**File:** `Sources/HyperImage/Convert/PreviewCard.swift:43-47`

**Issue:** When the selection changes, `.task(id: item.url)` cancels the old task. The awaited `Task.detached { … }.value` still finishes, though, and the old task then writes `info` with no check. If the previous file is slower to read (large RAW file, network volume), its result arrives after the new one. The card then shows file B's name next to file A's dimensions, size and date. Every other new `.task` in this diff (`RenameSummary`, `RenamePreviewSheet`) has `guard !Task.isCancelled`.

**Fix:**
```swift
let loaded = await Task.detached(priority: .utility) { PreviewInfo.load(url) }.value
guard !Task.isCancelled else { return }
info = loaded
```

### WR-03: Undo discards the remaining history after a partial failure, and the alert miscounts

**File:** `Sources/HyperImage/Rename/RenameActions.swift:19-35`

**Issue:**
- `lastRename = []` runs whatever the outcome. Files that were skipped (name taken) or failed can no longer be undone, even after the user frees the name.
- `skipped = total - outcome.renamed` counts real I/O failures too, and those same failures are listed again in `details`. The text always blames "o nome já está em uso", even when the file is missing or the move failed for another reason.
- `applyRename` also replaces `lastRename` with `outcome.moved` even when it is empty. A second rename that renames nothing silently wipes the undo of the first one.

**Fix:**
- Keep the moves that were not reversed: `lastRename = lastRename.filter { m in !outcome.moved.contains { $0.from == m.to } }`.
- Count conflicts (`plan.filter(\.conflict)`) separately from `outcome.failures`.
- In `applyRename`, only overwrite `lastRename` when `!outcome.moved.isEmpty`.

### WR-04: The extension from search and replace is never cleaned, and name length is never checked

**File:** `Sources/HyperImageCore/Naming/RenameTemplate.swift:82-84`, `Sources/HyperImageCore/Naming/BatchRename.swift:51-55`

**Issue:**
- `SearchReplaceRule.apply` passes the base name through `sanitized()` but returns `newExt` unchanged. An extension replacement containing `/` makes `"base.x/y"`, which `appendingPathComponent` treats as a subfolder path. A `:` creates a name that Finder shows with a `/`.
- An empty extension replacement turns `photo.jpg` into `photo`, with no warning.
- Neither path checks the 255-byte (UTF-8) limit on a file name. Repeating `*` or long `#` runs produce names that fail in phase 2, which feeds CR-01.

**Fix:** Clean `newExt` the same way (replace `/` and `:`). In `plan`, mark as a conflict any entry whose `name.utf8.count > 255`, or whose name is empty, `.` or `..`.

### WR-05: `RenamePanel` indexes `pairs[0...2]` without a bounds check, so restored state can crash it

**File:** `Sources/HyperImage/Rename/RenamePanel.swift:28-30`

**Issue:** `TolerantJSON` merges objects key by key, but a stored array replaces the default array entirely. If the saved `rename.searchReplace.pairs` holds fewer than 3 elements, opening the Renomear tab with the search-and-replace method traps with an index out of range. That can come from a damaged or hand-edited defaults file, or a later build that changes the number of pairs and is then downgraded. Nothing normalises the array after decoding.

**Fix:** Normalise after decoding, in `PersistedState.decode` or a custom `init(from:)` on `SearchReplaceRule`.
```swift
while state.rename.searchReplace.pairs.count < 3 { state.rename.searchReplace.pairs.append(.init()) }
```
Alternatively, have the view use `ForEach(settings.searchReplace.pairs.indices, id: \.self)`.

### WR-06: Output renaming plus the "Substituir" policy now silently overwrites unrelated originals

**File:** `Sources/HyperImageCore/Batch/ConvertSettings.swift:88-101`, `Sources/HyperImageCore/Batch/BatchConverter.swift:84`

**Issue:** `OutputPlanner` reserves only the paths of the queued inputs. Before this phase, output names came from each input's own name, so collisions with other files were rare. Now the default output template (`Image#####`) is the same as the default Batch Rename template. Consider this sequence:
1. The user batch-renames a folder to `Image00001.jpg…`.
2. Later they convert other images from the same folder in place, with "Renomear a saída" on and the "Substituir" policy.

Step 2 overwrites the renamed originals with `.atomic` writes, and nothing asks first. SAFE-01 is technically met (none of them are queued inputs), but this is the same data-loss class.

**Fix:** When `settings.rename` is on and the output folder is the input folder, either:
- reserve existing files on disk in `OutputPlanner`: use the `-N` counter while `FileManager.default.fileExists(atPath:)`, or
- force the "ask" policy and show a note in `OutputRenameRows`.

### WR-07: The rename preview counts entries as "a renomear" that are certain to fail

**File:** `Sources/HyperImage/Rename/RenamePreviewSheet.swift:26-28`

**Issue:** This follows from CR-01. `changes` counts entries whose destination is held by a skipped entry, so the user confirms a plan that partly fails, and with the current code can strand files. After the CR-01 fix, the count will be correct.

**Fix:** Covered by the CR-01 fix. Add a UI test that asserts the conflict count for the chain scenario.

## Info

### IN-01: `String(format: "%0Nd", Int)` truncates to 32 bits

**File:** `Sources/HyperImageCore/Naming/RenameTemplate.swift:36`

**Issue:** `%d` reads an `Int32`. I verified that `String(format: "%05d", 3_000_000_000)` gives `-1294967296`. The stepper caps the value at 9,999,999, but a persisted `startNumber` is not clamped.

**Fix:** Use `%0\(run)ld`, or clamp `startNumber` when decoding.

### IN-02: Templates can produce hidden or whitespace-only names

**File:** `Sources/HyperImageCore/Naming/RenameTemplate.swift:54-57`

**Issue:** `sanitized` does not trim spaces, and does not handle a leading `.`. A template such as `.x##` or `" "` produces hidden (`.x01.jpg`) or blank (` .jpg`) files.

**Fix:** Trim spaces and newlines, and strip leading dots. Fall back to `_`.

### IN-03: Saving `mode = .rename` resets every setting if the user downgrades

**File:** `Sources/HyperImageCore/Batch/OutputRecipe.swift:4`, `Sources/HyperImage/App/PersistedState.swift:33-35`

**Issue:** An older build that doesn't know `ConvertMode.rename` cannot decode the stored state. `decode` then falls back to `PersistedState()`, so all of the user's settings are lost, not just the mode.

**Fix:** Optional. Decode unknown enum values to a default, for example `ConvertMode(rawValue:) ?? .convert` in a custom `init(from:)`.

### IN-04: The "Converter" menu item opens the rename preview in Renomear mode

**File:** `Sources/HyperImage/App/HyperImageApp.swift:94`, `Sources/HyperImage/App/MainView.swift:93`

**Issue:** `startRequest` goes to `startConversion`, which redirects to `.renamePreview`. The menu label still says "Converter".

**Fix:** Use `mode.actionTitle` for the label.

### IN-05: The test named for swaps does not test a swap

**File:** `Tests/HyperImageCoreTests/NamingTests.swift:46-58`

**Issue:** `swapsNamesWithoutLosingFiles` only renames `a.txt -> c.txt`. The two-phase swap path, case-only renames (`a.JPG -> a.jpg`), and renames onto a skipped entry are not tested.

**Fix:** Add tests for `a<->b`, case-only renames, and the CR-01 chain.
