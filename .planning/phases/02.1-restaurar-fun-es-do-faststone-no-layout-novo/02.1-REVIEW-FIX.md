## Fixed Issues

### CR-01: Batch rename / undo can strand an original as a hidden, extension-less `.hyperimage-UUID` file

**Status:** fixed: requires human verification (logic change)
**Files modified:** `Sources/HyperImageCore/Naming/BatchRename.swift`, `Tests/HyperImageCoreTests/NamingTests.swift`
**Commit:** 3a99522
**Applied fix:**
- **Blocked chains are flagged in planning.** A new helper, `BatchRename.blockingChains`, runs until nothing changes. Any entry whose destination is the source of an entry that will not move (conflict or unchanged) is marked as a conflict too. Both `plan` and `undoPlan` use it.
- **Temporary names are visible.** They now look like `hyperimage-tmp-<UUID>.<ext>`: no leading dot, original extension kept.
- **A failed rollback no longer strands the file.** If the move back to the original name fails, the file goes to the first free `name (HyperImage N).ext` name. That move is recorded in `moved`, so undo and the input list stay consistent, and the failure message points to the file's new location.
- **Regression tests added (CR-01 and IN-05):**
  - the exact chain from the review (all 3 entries flagged, no files touched)
  - the undo chain with a recreated `photo.jpg`
  - a real `a<->b` swap with its undo
  - a case-only rename `a.JPG -> a.jpg` with its undo
  - a forced rollback failure that checks the visible rescue file
- **Test renamed.** The misnamed `swapsNamesWithoutLosingFiles` is now `renamesOneOfTwoFiles`.

### WR-01: Output renaming reads the EXIF date of every file on the main thread

**Files modified:** `Sources/HyperImageCore/Naming/RenameTemplate.swift`, `Sources/HyperImageCore/Batch/ConvertSettings.swift`, `Sources/HyperImageCore/Naming/BatchRename.swift`, `Sources/HyperImage/Convert/ConversionRunner.swift`, `Tests/HyperImageCoreTests/NamingTests.swift`
**Commit:** 6a23ef7
**Applied fix:**
- **Dates are read only when needed.** A new `RenameTemplate.usesDate` checks for a date token. `OutputPlanner` and `BatchRename.plan` read a file's date only when the template has one.
- **Records are built off the main actor.** `ConversionRunner.start` now builds the records in a `Task.detached` inside the run task. It checks the run generation and cancellation before converting.
- **Progress starts at 0.** While the records are being prepared, `progress` reports 0 instead of 1.

### WR-03: Undo discards the remaining history after a partial failure, and the alert miscounts

**Status:** fixed: requires human verification (logic change)
**Files modified:** `Sources/HyperImage/Rename/RenameActions.swift`, `Resources/Localizable.xcstrings`, `Tests/HyperImageAppTests/AppFlowTests.swift`
**Commit:** 4ae5f08
**Applied fix:**
- **History is kept after a partial undo.** The new `remainingHistory` drops moves that were reversed. If a file ended up somewhere else (a rescue), its move is re-pointed to that location. Moves whose file no longer exists are dropped. Undo can therefore be retried after the user frees the name.
- **Conflicts and I/O failures are counted separately.** Conflicts come from `plan.filter(\.conflict)`; I/O failures are listed after them.
- **The alert text changed.** The pt source string now says "o nome está em uso ou o arquivo não existe mais", and the en translation was updated to match. The old key was replaced in the xcstrings file.
- **`applyRename` keeps the previous undo when nothing moved.** It now overwrites `lastRename` only when `outcome.moved` is not empty.
- **App test added.** `partialUndoKeepsTheRestOfTheHistory` covers both behaviours.

### WR-04: The extension from search and replace is never cleaned, and name length is never checked

**Status:** fixed: requires human verification (logic change)
**Files modified:** `Sources/HyperImageCore/Naming/RenameTemplate.swift`, `Sources/HyperImageCore/Naming/BatchRename.swift`, `Tests/HyperImageCoreTests/NamingTests.swift`
**Commit:** bc4f4e4
**Applied fix:**
- **The replaced extension is cleaned.** `SearchReplaceRule.apply` now replaces `/` and `:` in it (`withoutSeparators`).
- **Invalid names are flagged in planning.** A new `RenameTemplate.isValidFileName` rejects empty names, `.`, `..` and names over 255 UTF-8 bytes. `plan` marks those entries as conflicts.
- **Tests added** for both.
- **Not changed: an empty extension replacement still removes the extension.** This can be intentional, and the preview shows the result. The preview's conflict tooltip still reads "Nome em conflito"; it was not reworded for invalid names.

### WR-05: `RenamePanel` indexes `pairs[0...2]` without a bounds check

**Commit:** e924fbb
**Applied fix:**
